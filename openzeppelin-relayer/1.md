# Worker和Relayer流程详解

系统实际上设置了四个不同职责的worker，它们与relayer共同构成了完整的交易处理流程。

## 四种Worker类型

从`initialize_workers.rs`中可以清楚看到四个专门的worker:

1. **Transaction Request Worker** (`TRANSACTION_REQUEST`)
   - 处理初始交易请求
   - 调用`transaction_request_handler`函数
   - 负责交易的初始验证和处理

2. **Transaction Submission Worker** (`TRANSACTION_SENDER`)
   - 处理交易的实际提交
   - 调用`transaction_submission_handler`函数
   - 负责签名交易并发送到区块链网络

3. **Transaction Status Worker** (`TRANSACTION_STATUS_CHECKER`)
   - 监控已提交交易的状态
   - 调用`transaction_status_handler`函数
   - 检查交易是否被确认或失败

4. **Notification Worker** (`NOTIFICATION_SENDER`)
   - 处理通知发送
   - 调用`notification_handler`函数
   - 在交易状态变化时发送webhook通知

**详细流程**:

1. **交易请求阶段**:
   - 用户通过API发送交易请求
   - Transaction Request Worker接收并验证请求
   - 创建初始交易记录(Pending状态)
   - 生成Transaction Submission任务, 加入队列

2. **交易提交阶段**:
   - Transaction Submission Worker接收提交任务
   - 确定使用哪个relayer处理交易
   - 使用relayer准备交易(计算nonce、签名等)
   - 将交易提交到区块链网络
   - 更新交易状态为Submitted
   - 生成Transaction Status检查任务

3. **交易状态监控阶段**:
   - Transaction Status Worker定期检查交易状态
   - 调用区块链RPC查询交易收据
   - 根据结果更新交易状态(Mined/Confirmed/Failed)
   - 如果未确认且时间过长，生成重提交任务给Transaction Submission Worker
   - 状态变化时生成通知任务

4. **通知阶段**:
   - Notification Worker处理通知任务
   - 向配置的webhook端点发送交易状态更新

### 重提交机制

当交易长时间未被确认时:
1. Transaction Status Worker检测到超时
2. 生成重提交任务
3. Transaction Submission Worker接收任务
4. 调用`calculate_bumped_gas_price`增加gas价格
5. 使用相同nonce重新提交交易

## Relayer和Worker的关系

- **Relayer**是区块链交互的核心，维护身份、私钥和nonce
- **Worker**是任务执行的单元，处理队列中的特定类型任务
- Worker**使用**Relayer执行实际区块链操作
- 每个Worker实例可以使用任何可用的Relayer
- 系统使用队列解耦请求处理和实际执行

## Worker配置细节

每个Worker配置了:
- 并发度(DEFAULT_CONCURRENCY = 2)
- 速率限制(每秒20个请求)
- 错误处理层(ErrorHandlingLayer)
- 重试策略(BackoffRetryPolicy)
- 应用状态数据(app_state)

这种架构设计使系统能够高效处理大量交易，保持可扩展性和可靠性，同时通过专门的worker处理不同阶段的任务。

# 一个relayer对应多个signer? 还是多个relayer对应一个signer?

您问得很好。从配置文件结构来看，这里的关系是：
一个relayer对应一个signer
从示例配置文件中可以看到:
每个relayer有一个signer_id字段，指向一个特定的signer
每个signer有一个对应的密钥文件
```json
{
  "id": "sepolia-example",
  "name": "Sepolia Example",
  "signer_id": "local-signer",   // 引用特定的signer
  ...
}
```

这样每个relayer就会使用不同的区块链地址发送交易，这样在追踪交易、管理余额和nonce时会更清晰。
如果多个relayer共用一个signer，会导致nonce管理混乱，因为它们会共享同一个发送地址。

# TransactionStatus::Failed的时候, 会做哪些操作?

当交易状态变为`TransactionStatus::Failed`时，系统会执行以下操作：

1. **更新交易状态**:
   在`handle_final_state`方法中，系统会调用`update_transaction_status_if_needed`将交易状态更新为`Failed`：
   ```rust
   async fn handle_final_state(
       &self,
       tx: TransactionRepoModel,
       status: TransactionStatus,
   ) -> Result<TransactionRepoModel, TransactionError> {
       self.update_transaction_status_if_needed(tx, status).await
   }
   ```

2. **更新内存记录**:
   在`update_transaction_status`方法中更新交易记录：
   ```rust
   let update_request = TransactionUpdateRequest {
       status: Some(new_status),
       confirmed_at: None, // 因为Failed状态不会有confirmed_at
       ..Default::default()
   };
   
   let updated_tx = self
       .transaction_repository()
       .partial_update(tx.id.clone(), update_request)
       .await?;
   ```

3. **发送通知**:
   如果配置了通知，系统会发送交易失败的通知：
   ```rust
   self.send_transaction_update_notification(&updated_tx).await?;
   ```

4. **不会调整nonce**:
   很重要的是，系统**不会**调整或重置已使用的nonce。当交易失败时：
   - 不会调用`decrement`方法减少nonce计数
   - 不会自动重新提交相同nonce的交易

5. **不会自动重试**：
   - 失败的交易会被标记为最终状态，不会进入重试循环
   - 如果需要重新尝试相同的操作，需要提交一个新的交易（使用新的nonce）

这种设计符合以太坊等区块链的nonce机制：即使交易失败，该nonce也被视为已使用，不能再次使用相同nonce发送交易。

如果您需要在交易失败后执行特定操作（如重试逻辑），您需要在应用层面实现这些逻辑，例如：
1. 监听交易状态
2. 当检测到`Failed`状态时，提交一个新的交易（使用新的nonce）
3. 可能的话，调整交易参数（如gas价格、gas限制等）来增加成功概率


# 什么时候should_resubmit?

根据`src/domain/transaction/evm/status.rs`中的实现，满足以下所有条件时才会返回`true`：

1. **交易必须处于`Submitted`状态**：
   ```rust
   if tx.status != TransactionStatus::Submitted {
       return Err(TransactionError::UnexpectedError(format!(
           "Transaction must be in Submitted status to resubmit, found: {:?}",
           tx.status
       )));
   }
   ```

2. **交易已等待足够长时间**：
   ```rust
   let age = get_age_of_sent_at(tx)?;
   let timeout = match tx.network_data.get_evm_transaction_data() {
       Ok(data) => get_resubmit_timeout_for_speed(&data.speed),
       Err(e) => return Err(e),
   };
   
   let timeout_with_backoff = get_resubmit_timeout_with_backoff(timeout, tx.hashes.len());
   if age > Duration::milliseconds(timeout_with_backoff) {
       info!("Transaction has been pending for too long, resubmitting");
       return Ok(true);
   }
   ```

### 超时计算逻辑

1. **基本超时根据交易速度决定**：
   - 通过`get_resubmit_timeout_for_speed`获取基本超时时间
   - 根据交易设置的速度（如`slow`、`medium`、`fast`）返回不同的超时时间

2. **添加退避机制**：
   - `get_resubmit_timeout_with_backoff`会根据已重试次数增加等待时间
   - 重试次数越多，等待时间越长，防止频繁重试
   - 重试次数通过`tx.hashes.len()`来判断（每次重提交都会记录一个新的交易哈希）

### 具体超时时间

从项目代码看，不同速度的超时设置大致如下：
- `slow`: 较长的超时（可能数十分钟）
- `medium`: 中等超时（几分钟）
- `fast`: 较短的超时（约1分钟）

然后，随着重试次数增加，这些基本超时值会被逐渐增加，形成退避策略。

### 调用流程

1. 交易状态机在`handle_submitted_state`中检查是否需要重提交：
   ```rust
   async fn handle_submitted_state(
       &self,
       tx: TransactionRepoModel,
   ) -> Result<TransactionRepoModel, TransactionError> {
       if self.should_resubmit(&tx).await? {
           return self.handle_resubmission(tx).await;
       }
       // ...
   }
   ```

2. 如果需要重提交，调用`handle_resubmission`处理：
   - 可能先创建一个NOOP交易（如果需要）
   - 然后发送重提交的作业

总结来说，只有当交易处于`Submitted`状态并且已经等待了足够长的时间（根据设定的速度和重试次数）才会触发重提交。这是为了解决网络拥堵或gas价格不足导致的交易长时间未被确认的问题。

# 在handle_resubmission的时候, 会增加gas重新发送吗?

是的，在`handle_resubmission`过程中，系统会增加gas价格重新发送交易。这个流程具体如下：

1. 首先，`handle_resubmission`本身创建重提交作业：
   ```rust
   async fn handle_resubmission(
       &self,
       tx: TransactionRepoModel,
   ) -> Result<TransactionRepoModel, TransactionError> {
       info!("Scheduling resubmit job for transaction: {}", tx.id);

       let tx_to_process = if self.should_noop(&tx).await? {
           self.process_noop_transaction(&tx).await?
       } else {
           tx
       };

       self.send_transaction_resubmit_job(&tx_to_process).await?;
       Ok(tx_to_process)
   }
   ```

2. 当重提交作业执行时，它会调用`resubmit_transaction`方法：
   ```rust
   async fn resubmit_transaction(
       &self,
       tx: TransactionRepoModel,
   ) -> Result<TransactionRepoModel, TransactionError> {
       info!("Resubmitting transaction: {:?}", tx.id);

       // 计算增加后的gas价格
       let bumped_price_params = self
           .price_calculator
           .calculate_bumped_gas_price(&tx, self.relayer())
           .await?;

       if !bumped_price_params.is_min_bumped.is_some_and(|b| b) {
           warn!(
               "Bumped gas price does not meet minimum requirement, skipping resubmission: {:?}",
               bumped_price_params
           );
           return Ok(tx);
       }

       // 获取交易数据
       let evm_data = tx.network_data.get_evm_transaction_data()?;

       // 创建新的带有提高gas价格的交易数据
       let updated_evm_data = evm_data.with_price_params(bumped_price_params);

       // 签名交易
       let sig_result = self
           .signer
           .sign_transaction(NetworkTransactionData::Evm(updated_evm_data.clone()))
           .await?;

       let final_evm_data = updated_evm_data.with_signed_transaction_data(sig_result.into_evm()?);

       // 发送原始交易
       let raw_tx = final_evm_data.raw.as_ref().ok_or_else(|| {
           TransactionError::InvalidType("Raw transaction data is missing".to_string())
       })?;

       self.provider.send_raw_transaction(raw_tx).await?;

       // 更新交易记录
       // ...
   }
   ```

重点是这个流程中的**gas价格增加**机制：

1. **调用专门的方法计算提高的gas价格**：
   ```rust
   let bumped_price_params = self
       .price_calculator
       .calculate_bumped_gas_price(&tx, self.relayer())
       .await?;
   ```

2. **验证gas增加是否足够**：
   ```rust
   if !bumped_price_params.is_min_bumped.is_some_and(|b| b) {
       warn!("Bumped gas price does not meet minimum requirement, skipping resubmission");
       return Ok(tx);
   }
   ```

3. **使用更高的gas价格创建新交易**：
   ```rust
   let updated_evm_data = evm_data.with_price_params(bumped_price_params);
   ```

系统会保持相同的nonce，但增加gas价格，这是以太坊覆盖之前未确认交易的标准方法。gas价格的具体增幅由`price_calculator`组件决定，通常会基于以下因素：

- 当前网络gas价格
- 原交易的gas价格
- 交易已等待的时间
- 先前重试次数
- 网络拥堵情况

这种机制确保在网络拥堵时能够逐渐提高交易的竞争力，增加被矿工打包的可能性。

# calculate_bumped_gas_price里面的逻辑是什么

`calculate_bumped_gas_price`方法的主要逻辑是计算交易重新提交时应使用的更高gas价格，它根据交易类型采用不同策略：

### 关键特性

1. **最小增加要求**：至少提高原gas价格的10%，确保新交易能替换旧交易
2. **市场价格比较**：如果当前市场价格更高，使用市场价格以提高成功率
3. **gas价格上限**：确保不超过配置的最大允许金额
4. **状态跟踪**：`is_min_bumped`标志指示是否满足最小增加要求
5. **额外费用**：某些网络可能需要额外费用，也会计算并添加

这种设计保证重新提交的交易有足够高的gas价格来替代之前的交易，同时通过上限机制防止费用过高。
